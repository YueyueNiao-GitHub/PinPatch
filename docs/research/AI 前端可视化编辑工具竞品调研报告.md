# AI 前端可视化编辑工具竞品调研报告

## 0. 核心结论

这次调研的出发点，不是再找一个“AI 前端编辑器”的大方向，而是先看清自然语言改前端页面时，最容易失控的是哪一步。

真实使用里，问题经常发生在很小的改动上：页面已经跑起来了，按钮大了一点，文案不太顺，或者某块间距看着别扭。人盯着浏览器，很清楚要改的是哪一块；但一回到 AI 对话框，只能写成一句“把这里调一下”。

这句话对人够用，对 AI 不够用。AI 可以生成代码，但它不知道“这里”对应哪个 DOM、哪个组件、哪个文件、哪段样式，只能自己猜。猜错以后，就会出现三类问题：改错位置、多处过度修改、部分未改完。

这个问题在非前端科班的研发 / 产业人员身上更明显。他们能在页面上看出样式、文案、布局问题，也知道自己想改哪里，但很难准确说出 DOM、class、组件名、文件路径和代码位置。结果就是：人看得见问题，AI 找不到锚点，IDE 里也缺少足够上下文。

所以这个工具的价值，不是再做一个可视化编辑器，也不是替代 IDE，而是补上自然语言改代码里最容易断的一段：把用户在页面上看到、点到的 UI 元素，转成 AI 和 IDE 能理解的修改上下文。

这段上下文至少包括：选中的页面元素、DOM、文本、样式、本地文件路径、组件链，以及用户补充的一句话修改意图。它的直接价值是降低定位成本，让 AI 少猜文件、少猜组件、少误改范围；对用户来说，就是不用先理解完整前端工程，也能把“我要改页面上这一块”表达清楚。

基于这个判断，第一阶段更适合做轻量浏览器插件：复用 React RA 的 HTML -> 本地路径 -> 组件链定位能力，补上“页面精准选中 -> 上下文传递 -> IDE / Agent 局部修改”这一步。用户还是在浏览器里看页面，在 VS Code / MS IDE / Copilot / CLI 等既有工具里改代码；插件只负责把“用户指的是哪里”说清楚，并把上下文送到后续修改流程里。

这也是为什么第一阶段不建议复刻 Inspector 这类一体化闭源 APP，也不建议重造 IDE。原因很直接：一体化形态体验好，但闭源、重、成本高；console / IDE 联动路线又会把用户绑到特定工具链里，和 B 端已有 VS Code、MS IDE、Copilot 等习惯冲突。现在最该验证的，是 React RA 的定位链路能不能让 AI 在局部改样式、改文案时少改错。

落地路径可以分三步：

| 阶段 | 目标 | 具体落点 |
|---|---|---|
| 第一阶段 | 验证页面精准定位和上下文传递是否有效 | 基于 React RA 做浏览器插件，支持页面选中、本地路径 / 组件链定位、DOM / 样式提取、结构化 prompt 生成，并调研一键填入 IDE / Agent 输入框 |
| 第二阶段 | 补齐可控修改闭环 | 在第一阶段成立后，加入预览、diff、撤销、Apply / Reject、MR / PR 等能力，避免页面变化和代码事实脱节 |
| 第三阶段 | 面向复杂业务场景增强上下文 | 接入设计系统 token、组件 props / variant、权限、路由、接口、日志和审计链路 |

第一阶段要尽量用真实场景测：localhost、纯 HTML 页面，再加 1-2 个真实产业研发页面。任务先选最常见的：改文案、改按钮大小、改间距、改颜色、调整局部布局。判断标准也要朴素一点：不要只看插件“能不能选中元素”，要看它相比纯自然语言 prompt，是否真的降低了改错、多改、漏改，文件定位和一次修改成功率有没有变好。

所以结论是：这个方向的起点不是“做一个更完整的编辑器”，而是解决自然语言改代码的定位问题。先用 React RA 浏览器插件验证“指得准、传得清、改得对”，确认价值成立后，再谈完整可视化编辑、Git / MR 闭环和复杂业务上下文。

## 一、调研背景与目标

这个方向不是先列竞品、再反推需求。它更多是被真实使用问题推着往前走。实际使用里已经能看到这类情况：用户在对话框里说“改这里”或“把这个样式调一下”，AI 会自己找代码改，但结果经常是改错位置、多改几处，或者只改了一半。

往前拆一步，用户先缺的是页面“指物”能力：能不能在页面上点准目标元素，再把这个定位结果带回改代码的流程里。尤其是非前端科班的研发 / 产业人员，他们能看出页面哪里不对，但很难说清 DOM、组件名、class、文件路径这些前端细节。

外部社区、AI coding 工具和 code-first design tools 的变化，也基本指向同一个问题：已有页面的局部修改还不够顺。哪怕只是调布局、改文案、改样式、换模块顺序，也经常要在页面表现、DOM、CSS、组件代码之间来回找。

所以这次调研不需要再证明“要不要做 AI 前端工具”。这里先把需求拆成一个能落地的问题：

> 如何让用户在真实页面上直接指出要改的位置，让 AI 自动拿到足够上下文，并把修改变成可预览、可审查、可回退的代码变更？

首批验证不必上来就做复杂工程项目。localhost 页面、纯 HTML 页面，以及产业研发日常遇到的改样式 / 改文案 / 局部调整场景就够了。只要能减少“查找元素 -> 定位代码 -> 传给 IDE / CLI -> 修改代码 -> 预览效果”这条链路里的来回折腾，就值得继续做。

所以这篇不按竞品清单来写，重点放在路线判断上：第一阶段先做完整工作台，还是先用 React RA 浏览器插件验证更轻的页面定位和上下文传递。

## 二、问题定义：我们到底要解决什么

如果一开始就把问题理解成“我们需要一个可视化编辑器”，路线很容易跑到低代码平台、Webflow、Figma 类构建器，甚至完整 IDE。

把问题落到执行层，是：

| 层级 | 表面问题 | 真实问题 |
|---|---|---|
| 用户表达 | 用户难以准确描述要改哪个 UI | 缺乏“指物”能力，AI 不知道用户指的是哪个元素 |
| AI 定位 | AI 能看代码，但不知道真实页面状态 | 缺少页面元素、DOM、样式、本地路径、组件链之间的稳定映射 |
| 局部修改 | 用户只想改指定区域 | 自然语言容易触发多处过度修改、改错位置或漏改 |
| 工具联动 | 页面能定位，但回到 IDE / CLI 输入仍断裂 | 缺少从浏览器选中结果到 IDE 输入框 / Agent 上下文的一键传递 |
| 组织协作 | 非前端科班研发 / 产业人员能看出问题，但难以说清代码位置 | 缺少顺应既有浏览器看样式 + IDE / CLI 改代码流程的轻量工具 |

这条路线先不碰拖拽编辑，先打通一条更轻的链路：

> 发现 UI 问题 -> 在浏览器中选中页面元素 -> 通过 React RA 定位本地路径和组件链 -> 将上下文填入 IDE / CLI / Agent -> 生成局部代码修改 -> 回到页面验证。

## 三、判断标准：什么叫可信的 AI 前端修改

这里不按“功能多少”评价竞品，主要看它能不能让修改结果可信。

code-first design tools 至少要过五个标准：

| 标准 | 含义 | 为什么重要 |
|---|---|---|
| Truthful 真实 | 面板展示的值必须与真实代码、CSS、组件状态一致 | 否则用户无法相信工具 |
| Deterministic 确定 | 同一操作应产生可预测结果 | 否则视觉编辑会变成不可控实验 |
| Unambiguous 清楚 | 当前选中对象、样式来源、修改范围必须明确 | 否则 Agent 容易改错位置 |
| Complete 完整 | 修改不能只停留在页面表面，必须落到稳定代码 | 否则没有工程交付价值 |
| Recoverable 可恢复 | 错误修改需要可审查、可撤销、可回滚 | 否则无法进入团队流程 |

因此 Inspector、Cursor Browser / MS IDE 类工具、React RA、React Grab、源码定位类工具都需要看一遍。它们各自覆盖了真实页面、元素选择、上下文采集、代码修改和审查链路的一段。但内部路线要收敛：第一阶段不替换 IDE，只用浏览器插件补上定位和上下文传递这一段。

## 四、竞品分层与纳入依据

这些产品不适合都叫“直接竞品”。更有用的分法，是看它们分别能给内部路线提供什么参考。

| 分层 | 产品 / 项目 | 类型 | 纳入原因 | 对内部的作用 |
|---|---|---|---|---|
| 体验终局对标 | Inspector | AI 前端可视化编辑器 | 最接近真实页面、元素选择、Agent 改代码、diff、Git/PR 的完整闭环 | 学习终局工作流，但不建议第一阶段完整复刻 |
| 第一阶段实现路径 | React RA 浏览器插件 | 页面元素定位 / 源码映射插件 | 已具备 HTML -> 本地路径 -> 组件链映射能力，可复用定位链路 | 第一阶段主路径：跨项目、前置零安装、尽量不改变用户 IDE 习惯 |
| 第一阶段参考样本 | React Grab | UI-to-Agent context 工具 | 证明“选中 UI 并复制上下文给 Agent”是独立高价值切口 | 参考轻量交互和上下文打包方式，不作为唯一实现路线 |
| IDE 路线 / 风险样本 | Cursor Browser / design sidebar、Curo、MS IDE / Copilot 类 | AI IDE 内置视觉编辑 / console 联动 | 说明 IDE 正在吸收视觉编辑能力，但往往要求用户进入特定工具链 | 学习意图采集，警惕工具绑定和可信度问题 |
| 开源工作台参考 | stagewise | Agentic IDE / 前端工作台 | 具备 Agent 工作区、浏览器上下文、diff review 等能力 | 可参考工作台和审查机制，但第一阶段不照搬重 IDE |
| 源码底盘能力 | code-inspector / react-dev-inspector / LocatorJS | 元素到源码定位 | 解决 DOM / 组件到源文件、行号、样式来源的映射 | 是 Agent 改对代码的底层基础 |
| 视觉编辑参考 | Onlook | Visual-first code editor | 面向设计师的视觉代码编辑器 | 可参考属性面板和设计师心智，但不作为主路线 |
| 上下文深度参考 | Frontman / Tidewave | Browser / framework runtime Agent | 强调 DOM、组件树、日志、路由、数据库等上下文 | 作为复杂业务后续能力边界 |
| 外围参考 | StackBlitz / Builder.io / Replay.io / Windsurf / Devin / Puck 等 | 环境、设计系统、调试、Agent IDE、Builder | 补足运行环境、设计系统、调试、组织协作等长期边界 | 不作为第一阶段直接竞品 |

## 五、核心竞品拆解

### 1. Inspector：终局体验对标

Inspector 值得看，原因不在某个单点功能，而在它把真实项目、页面元素选择、上下文采集、Agent 修改、预览、代码写回和 Git / PR 连成了一条完整链路。

其关键工作流是：

1. 用户打开本地项目或 GitHub 仓库。
2. 连接 Claude Code、Cursor、Codex 或 Inspector Agent。
3. 在浏览器中打开真实页面。
4. 点击页面元素，系统将 selected element 加入上下文。
5. 用户描述修改意图。
6. Agent 修改代码。
7. 用户预览和应用改动。
8. 通过 Git / PR 流程提交。

Inspector 可抽象为三层结构：

| 层级 | 说明 |
|---|---|
| Browser as Canvas | 真实页面既是画布，也是对象选择和结果验证环境 |
| Context as Bridge | 元素、截图、日志、文件、源码位置将视觉问题桥接给 Agent |
| Change as Reviewable Patch | 所有修改最终变成可审查、可撤销、可发布的代码变更 |

对内部来说，Inspector 给出的启发很直接：AI 前端修改需要先让用户在浏览器里“指物”。但它更像终局体验，第一阶段没必要照着完整复刻。

### 2. Cursor Browser / MS IDE 类：IDE 路线与风险样本

Cursor Browser / design sidebar、Curo、MS IDE / Copilot 这类能力，代表的是另一条路线：把视觉编辑或预览联动放进 IDE / console 工作流里。

它们有几个优点：

- 用户可以在 IDE 内看到真实页面。
- 用户可以选中页面元素，将其作为 Agent 上下文。
- Design / CSS 面板承接高频视觉调整。
- Agent 最终把视觉意图应用到代码中。

这条路线不适合作为第一阶段主线。B 端用户已经有 VS Code、MS IDE、Copilot、CLI 等习惯，强行迁移到某个 IDE 或重型工作台，采用成本会很高。第一阶段更适合顺着“浏览器看样式 + IDE / CLI 改代码”的主流程，在浏览器侧补一层轻量定位和上下文传递能力。

这类工具的主要风险集中在可信度：

| 风险 | 影响 |
|---|---|
| 面板值与真实 CSS 不一致 | 用户无法信任工具展示 |
| 视觉状态与代码结果脱节 | 看起来改了，但代码未稳定落地 |
| 复杂 layout / transform 处理失败 | 高级布局编辑不可靠 |
| 修改范围不清楚 | 用户不知道改动会影响哪里 |
| 缺少可恢复机制 | 错误修改难以进入团队流程 |

内部可以借鉴它的意图采集方式，但不能把视觉编辑当成最终交付。最终交付还是代码 diff。第一阶段也先不绑定单一 IDE，重点验证浏览器插件能不能把页面选中结果传给用户已有 IDE / CLI / Agent。

### 3. React RA 浏览器插件：第一阶段实现路径

第一阶段主路径可以从“参考 React Grab”再往前收一步：基于 React RA 做浏览器插件。React RA 已经有一条更贴近需求的定位链路：

- 支持从页面 HTML 定位到本地路径。
- 支持从页面元素追溯组件链。
- 能辅助 AI 解读项目结构，减少“猜文件、猜组件”。
- 有项目内安装和浏览器插件两种形态，其中浏览器插件更适合跨项目使用，前置成本更低。

React RA 现在主要断在交互上：页面里能选中、能定位，但用户还要手动回到 IDE / CLI 输入框组织提示词。第一阶段要补的就是这个断点，别从零做一个 IDE 或完整视觉编辑器。

第一阶段要验证的问题变为：

> 当用户在页面中精准选中目标元素，并由 React RA 插件自动提供本地路径、组件链、DOM、样式和修改意图时，AI 是否能更稳定地完成局部样式 / 文案修改？

第一阶段能力范围包括：

- 页面元素选择与高亮，解决“选不准”。
- DOM、文本、样式、选择器提取。
- HTML -> 本地路径 -> 组件链映射。
- 将选中结果和用户补充意图打包为结构化 prompt。
- 调研一键填入 IDE / Copilot / Cursor / CLI 输入框的可行性。
- 在 localhost、纯 HTML、真实产业研发页面中验证定位准确性和修改命中率。

React Grab 仍然值得参考，但它更像 UI-to-Agent context 的产品样本。内部第一阶段不照搬它，可以用 React RA 的定位能力做底座，再吸收 React Grab 那种“选中元素 + 补一句上下文 + 交给外部 Agent”的轻交互。

### 4. 源码定位类工具：底盘能力参考

code-inspector、react-dev-inspector、LocatorJS 解决的是另一个底层问题：

> 用户在页面上点击一个元素后，系统如何知道它对应哪个组件、哪个文件、哪一行代码？

这类工具还不是完整 AI 修改产品，但会影响内部方案的底层可靠性。没有稳定的元素到源码映射，Agent 修改就容易猜文件、猜组件、猜样式来源。

可参考能力包括：

- 编译期注入。
- Source Map。
- DOM 属性标记。
- React 组件树关联。
- IDE bridge。
- 文件和行号跳转。

### 5. stagewise：开源工作台参考

stagewise 更像一个 agentic IDE / frontend workbench。它强在 Agent 工作区、文件探索、diff review、多模型 / BYOK 支持，以及代码变更管理。

可学习点：

- Agent 工作区。
- 代码 diff 审查。
- 多模型和本地工具链接入。
- 面向开发者的协作流程。

但它太像 IDE，不适合作为内部产品的第一心智。内部方向如果要兼顾设计、产品和研发协作，就不要太早进入完整 IDE 形态。

### 6. Onlook：视觉编辑体验参考

Onlook 代表 visual-first code editor 路线，更接近面向设计师的视觉代码编辑器，强调画布、属性面板、组件库、Tailwind / 样式编辑等能力。

可参考点：

- 视觉属性面板。
- 画布式编辑体验。
- 设计师更容易理解的操作方式。
- 组件化编辑体验。

但它也提醒我们：如果过度强调视觉编辑，产品很容易滑向 builder / 低代码平台，离“修改真实代码库里的已有 UI”越来越远。

### 7. Frontman / Tidewave：复杂上下文边界参考

Frontman 和 Tidewave 提醒的是后续边界：复杂业务系统里的 AI 修改，光有 DOM 和 CSS 不够。

后续可能需要的上下文包括：

- 路由。
- 服务端日志。
- 接口请求。
- 数据库状态。
- framework metadata。
- 组件状态。
- 权限与角色。
- 构建输出。
- 运行时错误。

这些能力先不放进第一阶段，可以作为第三阶段复杂业务场景的能力边界。

## 六、横向能力对照

只看“有没有 Chat / 属性面板 / 浏览器”不够。这里更关心的是，它能不能让修改结果可信。

| 能力维度 | 关注问题 | 内部判断 |
|---|---|---|
| 真实页面上下文 | 能否拿到用户实际看到的 DOM、样式、截图、状态 | 第一阶段必须验证 |
| 元素到源码映射 | 能否定位组件、文件、行号和样式来源 | 复用 React RA 的 HTML -> 本地路径 -> 组件链能力，是第一阶段底盘 |
| Agent 接入方式 | 是内置 Agent，还是把上下文交给外部 IDE / CLI / Agent | 第一阶段不内置重型 IDE，优先适配用户已有工具 |
| 视觉意图表达 | 用户能否点选、标注、补一句自然语言 | 是降低非前端科班用户表达成本的核心 |
| IDE 输入联动 | 能否将选中元素上下文一键填入 IDE / Copilot / Cursor / CLI 输入框 | 是解决“页面选中 -> 回 IDE 输入”断层的关键验证项 |
| 代码可控性 | 是否支持 diff、撤销、回滚、审查 | 第二阶段重点补齐 |
| Git / MR 流程 | 是否能进入团队代码协作链路 | 第二阶段后期再做 |
| 设计系统约束 | 是否理解 token、组件 variant、props | 第三阶段能力 |
| 复杂业务上下文 | 是否理解权限、路由、日志、接口、数据状态 | 第三阶段能力 |

## 七、内部路线建议

内部不需要直接复刻完整 Inspector，也不该强迫用户换 IDE。建议先基于 React RA 做轻量浏览器插件，把页面精准定位和上下文传递跑通，再看是否需要补浏览器工作台和复杂业务上下文。

### 阶段一：React RA 浏览器插件

目标：

> 验证“非前端科班研发 / 产业人员在页面中选中 UI 后，React RA 插件是否能提供足够准确的定位上下文，并提高 Agent 局部改样式 / 文案的命中率”。

能力范围：

- 页面元素选择。
- 高亮当前选中对象。
- 提取 DOM、文本、样式、选择器。
- 复用 React RA 提取本地路径、组件链和文件线索。
- 允许用户补充一句自然语言意图。
- 将上下文复制或一键填入外部 IDE / Copilot / Cursor / CLI 输入框。
- 用户回到页面或 IDE 验证结果。

暂不做：

- 完整 Git / PR。
- 多项目管理。
- 复杂权限。
- 全栈日志。
- 数据库上下文。
- 完整设计器属性面板。
- 强绑定某个特定 IDE。

### 阶段二：Browser-first 修改闭环

如果第一阶段验证成立，再补完整修改闭环：

- 页面内预览。
- 修改前后对比。
- diff 审查。
- undo / rollback。
- apply / reject。
- MR / PR 提交。
- 与内部代码平台或 CI 流程连接。

### 阶段三：复杂业务上下文

再往后，面向复杂后台和内部真实业务系统，可以继续接：

- 设计系统 token。
- 组件 props / variant。
- 业务语义。
- 权限状态。
- 路由。
- 接口请求。
- console / network 日志。
- 服务端日志。
- 审计链路。

## 八、第一阶段 MVP 验证方案

| 项目 | 建议 |
|---|---|
| 验证目标 | 判断 React RA 浏览器插件是否能提升页面局部改样式 / 文案的定位准确率和修改命中率 |
| 目标用户 | 非前端科班的研发 / 产业人员，以及需要偶发修改页面样式、文案、布局的业务研发 |
| 试点页面 | localhost 项目、纯 HTML 页面、1-2 个真实产业研发页面，不只用 demo |
| 典型任务 | 改文案、改按钮大小、改间距、改颜色、调整局部布局、定位组件文件 |
| 对照基线 | 纯自然语言 prompt，不提供页面选中和 React RA 定位上下文 |
| 实验组 | 提供选中元素、DOM、样式、文本、选择器、本地路径、组件链、用户补充意图 |
| 关键交互验证 | 调研插件一键填入指定 IDE / Copilot / Cursor / CLI 输入框的可行性、权限限制和稳定性 |
| 成功指标 | 元素定位准确率、文件定位准确率、一次修改成功率、误改率、漏改率、人工修正次数、预览验证耗时 |
| 失败条件 | 页面选中不稳定、React RA 映射不准、一键填入不可行，或 Agent 修改准确率没有明显提升 |
| 参与角色 | 研发侧为主，重点访谈非前端科班研发 / 产业人员；前端同学参与结果审查 |
| 不做范围 | 完整工作台、完整属性面板、完整 Git / PR、多项目管理、强绑定某个 IDE |

MVP 不用证明“我们能做一个可视化编辑器”。它先证明一件事：

> AI 在拿到 React RA 提供的页面定位上下文后，是否真的改得更准、更快、更可控。

## 九、风险与边界

### 1. 正确性风险

风险：工具展示的样式、DOM、组件信息和真实代码对不上。  
应对：先验证真实样式读取、源码定位和 diff 可审查。

### 2. 工程接入风险

风险：只在干净 demo 里有效，到了真实业务页面就失效。  
应对：第一阶段就选 localhost、纯 HTML 和真实产业研发页面试点，避免纯 demo 验证。

### 3. 产品边界风险

风险：做着做着滑向低代码平台、完整 IDE 或纯视觉属性面板。  
应对：始终坚持“浏览器精准定位 + IDE / CLI 局部改代码”的主线，不重造 IDE，不做完整低代码编辑器。

### 4. 组织采用风险

风险：非前端科班研发 / 产业人员能指出页面问题，但不一定判断得出 AI 是否改对；前端开发者也可能不敢接受自动修改。  
应对：第一阶段先验证定位和上下文是否准确，复杂修改仍回到 IDE / CLI，由开发者审查代码变更。

### 5. 设计系统漂移风险

风险：用户通过视觉编辑改出不符合设计系统的任意样式。  
应对：后续接入 token、组件 variant 和内部设计系统约束。

### 6. 插件与 IDE 联动风险

风险：浏览器插件跨项目使用方便，但一键填入 IDE / Copilot / Cursor / CLI 输入框，可能会被浏览器权限、IDE 安全策略、输入框 DOM 差异和系统级自动化限制卡住。  
应对：将“一键填入”作为独立技术验证项；若不可行，先采用复制结构化 prompt、打开本地协议、调用 CLI 或生成可粘贴上下文等降级方案。

## 十一、最终建议与下一步

这次调研最后收敛到一个判断：内部第一阶段不用追求完整 AI 前端可视化编辑器，先基于 React RA 做浏览器插件，验证页面精准定位和上下文传递能力。

先解决“用户在页面上指哪里，AI 就知道该改哪里，并尽量只改指定区域”的问题，再讨论完整工作台、视觉属性面板、Git / PR 闭环和复杂业务上下文。

对应路线如下：

1. 第一阶段：React RA 浏览器插件 + 页面元素选择 + 本地路径 / 组件链 / DOM / 样式上下文 + 外部 IDE / Agent 修改。
2. 第二阶段：Browser-first 修改闭环，加入预览、diff、撤销、MR。
3. 第三阶段：接入设计系统、业务语义、权限、路由、日志、接口上下文。

这里的分工可以这样看：Inspector 看终局体验，React RA 浏览器插件做第一阶段实现路径，React Grab 参考轻量 UI-to-Agent context，源码定位类项目看底层能力，Cursor Browser / MS IDE 类看 IDE 路线和可信度风险，Onlook、stagewise、Frontman、Tidewave 补足视觉编辑、Agent 工作台和复杂上下文边界。

下一步不要继续扩大竞品列表，应该进入 MVP 验证：

1. 调研基于 React RA 浏览器插件一键填入指定 IDE / Copilot / Cursor / CLI 输入框的技术可行性和限制。
2. 与研发侧沟通，梳理除 localhost、纯 HTML 外，产业研发在页面改样式 / 文案时的典型场景。
3. 选取 1-2 个真实页面，对比“纯 prompt 修改”和“带 React RA 页面定位上下文修改”的准确率、耗时、误改率和可审查性。
