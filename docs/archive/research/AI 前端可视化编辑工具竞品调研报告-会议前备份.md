# AI 前端可视化编辑工具竞品调研报告

## 0. 核心结论

本次调研的核心结论是：这个方向值得做，但第一阶段不应从“完整 AI 前端可视化编辑器”起步。真正需要先验证的，不是能否做出一个类似 Inspector 的完整工作台，而是能否解决最关键的一步：用户在真实页面上指出一个 UI 后，AI 是否能拿到足够准确的页面、样式和源码上下文，并因此更稳定地改对代码。

换句话说，第一阶段应优先建设一层 **UI 上下文能力**：把用户看到的页面元素，转换成 Agent 能理解和使用的结构化信息，包括 DOM、样式、组件关系、源码位置和必要的视觉状态。这个能力如果不成立，后续无论是视觉属性面板、Browser-first 工作台，还是 Git / MR 闭环，都会缺少可信基础。

如果验证结果成立，再逐步扩展为完整修改闭环：在浏览器中预览改动，通过 diff 审查和撤销机制控制风险，并进一步接入设计系统、权限、路由、日志、接口等复杂业务上下文。

### 核心判断

1. **方向成立**  
   AI 前端修改的关键痛点不是“不会生成代码”，而是缺少真实页面、运行时状态和源码之间的上下文桥接。

2. **第一阶段不应复刻 Inspector**  
   Inspector 是终局体验参考，但第一阶段更应学习 React Grab 和源码定位类工具，先验证“选中 UI + 结构化上下文 + Agent 修改”这一最小切口。

3. **可信修改比功能覆盖更重要**  
   code-first design tools 的关键门槛不是是否有属性面板、拖拽或 Chat，而是修改是否真实、确定、清楚、完整、可恢复。

4. **内部机会在复杂业务环境**  
   外部工具难以覆盖私有代码、内部组件库、设计系统 token、权限状态、复杂后台语义、MR / CI / 审计链路，这正是内部工具的机会。

5. **推荐路线**  
   第一阶段验证 UI 上下文能力；第二阶段补 Browser-first 修改闭环；第三阶段接入设计系统和业务上下文。

## 一、调研背景与目标

这一方向并非单纯从外部竞品分析倒推出来，而是由内外部反馈共同指向：一方面，团队内部真实工作场景中已经反复出现类似编辑痛点；另一方面，外部社区、AI coding 工具和 code-first design tools 的演进也说明，这不是单个团队的局部问题，而是前端 AI 修改场景中的共性需求。当用户已有 HTML 或前端页面时，进行局部修改仍十分困难。即使只是调整布局、文案、样式、模块顺序或局部视觉状态，也经常需要在页面表现、DOM 结构、CSS、组件代码之间来回切换。

因此，本次调研的核心目标并非论证“是否需要开发 AI 前端工具”，而是将这一已存在的需求拆解为可落地的具体问题：

> 如何让用户在真实页面上直接指出要改的位置，让 AI 自动拿到足够上下文，并把修改变成可预览、可审查、可回退的代码变更？

该需求的首批验证对象不必是复杂工程项目，而可聚焦于更贴近日常痛点的 HTML 或简单前端页面编辑场景。只要能显著降低“查找元素 -> 调整样式 -> 修改代码 -> 预览效果”这一闭环的往返成本，就具备持续推进的价值。

本次调研不是为了罗列市面上的 AI 前端工具，而是为了支撑一个更具体的路线判断：第一阶段到底应该先做完整工作台，还是先验证更轻量的 UI 上下文层。

## 二、问题定义：我们到底要解决什么

如果将问题简单理解为“我们需要一个可视化编辑器”，就容易误入低代码平台、Webflow、Figma 类构建器，甚至完整 IDE 的路径。

更准确的问题还原是：

| 层级 | 表面问题 | 真实问题 |
|---|---|---|
| 用户表达 | 用户难以准确描述要改哪个 UI | 缺乏“指物”能力，AI 不知道用户指的是哪个元素 |
| AI 理解 | AI 能看代码，但不知道真实页面状态 | 缺少 DOM、样式、截图、组件关系、运行时上下文 |
| 视觉编辑 | 面板看起来能改 UI | 面板值可能和真实 CSS / 组件状态不一致 |
| 代码落地 | AI 能生成代码 | 修改范围、diff、回滚、提交链路不清楚 |
| 组织协作 | 设计、产品、前端反复截图沟通 | 缺少从视觉问题到代码修改的统一工作流 |

因此，本方向的核心不是“让页面能被拖拽编辑”，而是建立一条链路：

> 发现 UI 问题 -> 指向页面元素 -> 收集上下文 -> 提交给 AI -> 生成代码修改 -> 预览 / 审查 -> 回滚 / 提交。

## 三、判断标准：什么叫可信的 AI 前端修改

本报告不按“功能多少”评价竞品，而按其是否能形成可信修改来判断。

code-first design tools 至少需要满足五个标准：

| 标准 | 含义 | 为什么重要 |
|---|---|---|
| Truthful 真实 | 面板展示的值必须与真实代码、CSS、组件状态一致 | 否则用户无法相信工具 |
| Deterministic 确定 | 同一操作应产生可预测结果 | 否则视觉编辑会变成不可控实验 |
| Unambiguous 清楚 | 当前选中对象、样式来源、修改范围必须明确 | 否则 Agent 容易改错位置 |
| Complete 完整 | 修改不能只停留在页面表面，必须落到稳定代码 | 否则没有工程交付价值 |
| Recoverable 可恢复 | 错误修改需要可审查、可撤销、可回滚 | 否则无法进入团队流程 |

这也是为什么 Inspector、Cursor Browser、React Grab、源码定位类工具都值得分析：它们分别覆盖了真实页面、元素选择、上下文采集、代码修改和可信审查链路中的不同环节。

## 四、竞品分层与纳入依据

本报告不将所有产品简单归为“直接竞品”，而是依据其对内部路线判断的作用进行分层。

| 分层 | 产品 / 项目 | 类型 | 纳入原因 | 对内部的作用 |
|---|---|---|---|---|
| 体验终局对标 | Inspector | AI 前端可视化编辑器 | 最接近真实页面、元素选择、Agent 改代码、diff、Git/PR 的完整闭环 | 学习终局工作流，但不建议第一阶段完整复刻 |
| 第一阶段 MVP 参考 | React Grab | UI-to-Agent context 工具 | 证明“选中 UI 并复制上下文给 Agent”是独立高价值切口 | 第一阶段最重要参照 |
| IDE 路线 / 风险样本 | Cursor Browser / design sidebar | AI IDE 内置视觉编辑 | 说明 IDE 正在吸收视觉编辑能力，也暴露正确性风险 | 学习意图采集，警惕可信度问题 |
| 开源工作台参考 | stagewise | Agentic IDE / 前端工作台 | 具备 Agent 工作区、浏览器上下文、diff review 等能力 | 可参考工作台和审查机制，不应照搬重 IDE |

| 视觉编辑参考 | Onlook | Visual-first code editor | 面向设计师的视觉代码编辑器 | 可参考属性面板和设计师心智，但不作为主路线 |
| 上下文深度参考 | Frontman / Tidewave | Browser / framework runtime Agent | 强调 DOM、组件树、日志、路由、数据库等上下文 | 作为复杂业务后续能力边界 |
| 外围参考 | StackBlitz / Builder.io / Replay.io / Windsurf / Devin / Puck 等 | 环境、设计系统、调试、Agent IDE、Builder | 补足运行环境、设计系统、调试、组织协作等长期边界 | 不作为第一阶段直接竞品 |

## 五、核心竞品拆解

### 1. Inspector：终局体验对标

Inspector 的价值不在于某个单点功能，而在于把真实项目、页面元素选择、上下文采集、Agent 修改、预览、代码写回及 Git / PR 流程串联成闭环。

其关键工作流是：

1. 用户打开本地项目或 GitHub 仓库。
2. 连接 Claude Code、Cursor、Codex 或 Inspector Agent。
3. 在浏览器中打开真实页面。
4. 点击页面元素，系统将 selected element 加入上下文。
5. 用户描述修改意图。
6. Agent 修改代码。
7. 用户预览和应用改动。
8. 通过 Git / PR 流程提交。

Inspector 可抽象为三层结构：

| 层级 | 说明 |
|---|---|
| Browser as Canvas | 真实页面既是画布，也是对象选择和结果验证环境 |
| Context as Bridge | 元素、截图、日志、文件、源码位置将视觉问题桥接给 Agent |
| Change as Reviewable Patch | 所有修改最终变成可审查、可撤销、可发布的代码变更 |

对内部的启发是：Inspector 证明“在浏览器中指物”是 AI 前端修改的关键入口。但它是终局体验，不是第一阶段应该直接复刻的完整形态。

### 2. Cursor Browser / design sidebar：IDE 路线与风险样本

Cursor Browser / design sidebar 代表的是 AI IDE 内置视觉编辑能力的路线。它将真实浏览器、元素选择、Design / CSS 面板、Agent 修改、代码应用整合在 IDE 中。

它的价值在于：

- 用户可以在 IDE 内看到真实页面。
- 用户可以选中页面元素，将其作为 Agent 上下文。
- Design / CSS 面板承接高频视觉调整。
- Agent 最终把视觉意图应用到代码中。

但它暴露的关键风险不是“功能不够”，而是“可信度不足”：

| 风险 | 影响 |
|---|---|
| 面板值与真实 CSS 不一致 | 用户无法信任工具展示 |
| 视觉状态与代码结果脱节 | 看起来改了，但代码未稳定落地 |
| 复杂 layout / transform 处理失败 | 高级布局编辑不可靠 |
| 修改范围不清楚 | 用户不知道改动会影响哪里 |
| 缺少可恢复机制 | 错误修改难以进入团队流程 |

对内部的启发是：视觉编辑应作为意图采集层，而不是最终交付层。真正的交付物仍应是可审查的代码 diff。

### 3. React Grab：第一阶段 MVP 主参照

React Grab 的价值在于把问题切得足够小：

> 用户选中任意 UI 元素，工具复制该元素相关上下文，并交给外部 Agent 使用。

这正好对应内部第一阶段需要验证的关键假设：

> 当 Agent 获得更准确的 UI 上下文后，是否能更稳定地定位文件并完成修改？

它不提供完整修改闭环，也不承担 Git / PR / diff / 回滚。但正因为轻量，它适合作为第一阶段 MVP 参照。

第一阶段可学习的能力包括：

- 页面元素选择。
- DOM 结构提取。
- 文本内容提取。
- 样式信息提取。
- 选择器或组件线索。
- 源码位置线索。
- 将上下文打包给外部 Agent。

### 4. 源码定位类工具：底盘能力参考

code-inspector、react-dev-inspector、LocatorJS 等工具解决的是另一个底层问题：

> 用户在页面上点击一个元素后，系统如何知道它对应哪个组件、哪个文件、哪一行代码？

这类工具不是完整 AI 修改产品，但对内部方向非常关键。没有稳定的元素到源码映射，Agent 修改就容易变成猜文件、猜组件、猜样式来源。

可参考能力包括：

- 编译期注入。
- Source Map。
- DOM 属性标记。
- React 组件树关联。
- IDE bridge。
- 文件和行号跳转。

### 5. stagewise：开源工作台参考

stagewise 更像一个 agentic IDE / frontend workbench。它的强项在于 Agent 工作区、文件探索、diff review、多模型 / BYOK 支持，以及代码变更管理。

可学习点：

- Agent 工作区。
- 代码 diff 审查。
- 多模型和本地工具链接入。
- 面向开发者的协作流程。

但它的 IDE 化较重，不适合作为内部产品的第一心智。内部方向如果面向设计、产品、前端协作，应避免过早进入完整 IDE 形态。

### 6. Onlook：视觉编辑体验参考

Onlook 代表 visual-first code editor 路线。它更接近面向设计师的视觉代码编辑器，强调画布、属性面板、组件库、Tailwind / 样式编辑等能力。

可参考点：

- 视觉属性面板。
- 画布式编辑体验。
- 设计师更容易理解的操作方式。
- 组件化编辑体验。

但它也提示一个风险：如果过度强调视觉编辑，产品容易滑向 builder / 低代码平台，而不是“修改真实代码库中的已有 UI”。

### 7. Frontman / Tidewave：复杂上下文边界参考

Frontman 和 Tidewave 提醒我们：复杂业务系统里的 AI 修改不只需要 DOM 和 CSS。

后续可能需要的上下文包括：

- 路由。
- 服务端日志。
- 接口请求。
- 数据库状态。
- framework metadata。
- 组件状态。
- 权限与角色。
- 构建输出。
- 运行时错误。

这些能力不应进入第一阶段，但应作为第三阶段复杂业务场景的能力边界。

## 六、横向能力对照

真正拉开差距的不是“有没有 Chat / 属性面板 / 浏览器”，而是是否能形成可信修改。

| 能力维度 | 关注问题 | 内部判断 |
|---|---|---|
| 真实页面上下文 | 能否拿到用户实际看到的 DOM、样式、截图、状态 | 第一阶段必须验证 |
| 元素到源码映射 | 能否定位组件、文件、行号和样式来源 | 是 Agent 改对代码的底盘 |
| Agent 接入方式 | 是内置 Agent，还是把上下文交给外部 Agent | 第一阶段可先接外部 Agent |
| 视觉意图表达 | 用户能否点选、标注、补一句自然语言 | 是降低表达成本的核心 |
| 代码可控性 | 是否支持 diff、撤销、回滚、审查 | 第二阶段重点补齐 |
| Git / MR 流程 | 是否能进入团队代码协作链路 | 第二阶段后期再做 |
| 设计系统约束 | 是否理解 token、组件 variant、props | 第三阶段能力 |
| 复杂业务上下文 | 是否理解权限、路由、日志、接口、数据状态 | 第三阶段能力 |

## 七、内部路线建议

内部不应直接复刻完整 Inspector。更稳妥的路径是先验证轻量上下文层，再逐步补齐浏览器工作台和复杂业务上下文。

### 阶段一：UI 上下文能力

目标：

> 验证“用户选中 UI 后，结构化上下文是否能显著提升 Agent 修改准确率”。

能力范围：

- 页面元素选择。
- 高亮当前选中对象。
- 提取 DOM、文本、样式、选择器。
- 尝试提取组件 / 文件线索。
- 允许用户补充一句自然语言意图。
- 将上下文复制或传递给外部 Agent。
- 用户回到页面或 IDE 验证结果。

暂不做：

- 完整 Git / PR。
- 多项目管理。
- 复杂权限。
- 全栈日志。
- 数据库上下文。
- 完整设计器属性面板。

### 阶段二：Browser-first 修改闭环

当第一阶段验证成立后，再补完整修改闭环：

- 页面内预览。
- 修改前后对比。
- diff 审查。
- undo / rollback。
- apply / reject。
- MR / PR 提交。
- 与内部代码平台或 CI 流程连接。

### 阶段三：复杂业务上下文

面向复杂后台和内部真实业务系统，进一步接入：

- 设计系统 token。
- 组件 props / variant。
- 业务语义。
- 权限状态。
- 路由。
- 接口请求。
- console / network 日志。
- 服务端日志。
- 审计链路。

## 八、第一阶段 MVP 验证方案

| 项目 | 建议 |
|---|---|
| 验证目标 | 判断 UI 上下文能力是否能提升 Agent 前端修改准确率 |
| 试点页面 | 1-2 个真实 HTML / 简单前端页面，不只用 demo |
| 典型任务 | 改文案、改按钮大小、改间距、改颜色、调整模块顺序、定位组件文件 |
| 对照基线 | 纯自然语言 prompt，不提供 UI 上下文 |
| 实验组 | 提供选中元素、DOM、样式、文本、选择器、组件 / 文件线索 |
| 成功指标 | 文件定位准确率、一次修改成功率、人工修正次数、预览验证耗时 |
| 失败条件 | 上下文无法稳定提取，或 Agent 修改准确率没有明显提升 |
| 参与角色 | 前端为主，设计 / 产品作为问题提出方参与验证 |
| 不做范围 | 完整工作台、完整属性面板、完整 Git / PR、多项目管理 |

MVP 的核心不是证明“我们能做一个可视化编辑器”，而是证明：

> AI 在拿到 UI 上下文后，是否真的改得更准、更快、更可控。

## 九、风险与边界

### 1. 正确性风险

风险：工具展示的样式、DOM、组件信息与真实代码不一致。  
应对：优先验证真实样式读取、源码定位、diff 可审查。

### 2. 工程接入风险

风险：只在干净 demo 中有效，到真实业务页面失效。  
应对：第一阶段就选真实页面试点，避免纯 demo 验证。

### 3. 产品边界风险

风险：滑向低代码平台、完整 IDE 或纯视觉属性面板。  
应对：始终坚持“修改真实页面 / 真实代码”的主线。

### 4. 组织采用风险

风险：非工程用户能提出问题，但开发者不敢接受自动修改。  
应对：先让开发者可审查，再逐步降低设计和产品参与门槛。

### 5. 设计系统漂移风险

风险：用户通过视觉编辑产生不符合设计系统的任意样式。  
应对：后续接入 token、组件 variant 和内部设计系统约束。

外部价格和商业化信息不能直接证明内部方向必然成立，但能作为价值信号：

| 产品 | 信号 | 说明 |
|---|---|---|
| Cursor | Team / Enterprise 定价 | AI coding 已进入团队预算 |
| v0 | Team / Business 定价 | AI UI 生成具备持续付费意愿 |
| stagewise | Pro / Ultra 定价 | Agentic 前端工作流具备付费空间 |
| Onlook | Team / Enterprise | 真实代码视觉编辑具备团队价值 |
| Claude / Codex 类工具 | 多档订阅和团队方案 | AI 编码能力已成为持续性投入 |

这说明市场不是只为“生成代码”付费，而是为更高质量的开发上下文、团队协作、安全治理和真实代码工作流付费。

但内部立项不能只依赖外部价格信号，最终仍需通过 MVP 验证修改准确率、效率和可审查性。

---

## 十一、结论回收

本次调研最终指向一个更收敛的产品判断：内部第一阶段不应追求完整 AI 前端可视化编辑器，而应优先验证 UI 上下文能力。

也就是说，先解决“用户指哪里，AI 就知道改哪里”的问题，再讨论完整工作台、视觉属性面板、Git / PR 闭环和复杂业务上下文。

对应路线如下：

1. 第一阶段：页面元素选择 + DOM / 样式 / 源码上下文 + Agent 修改。
2. 第二阶段：Browser-first 修改闭环，加入预览、diff、撤销、MR。
3. 第三阶段：接入设计系统、业务语义、权限、路由、日志、接口上下文。

因此，Inspector 是终局体验参考，React Grab 是第一阶段 MVP 参照，源码定位类项目是底层能力参考，Cursor Browser / design sidebar 是 IDE 路线与可信度风险样本，Onlook、stagewise、Frontman、Tidewave 等则用于补足视觉编辑、Agent 工作台和复杂上下文边界。

下一步建议不是继续扩大竞品列表，而是进入 MVP 验证：选取 1-2 个真实 HTML / 简单前端页面，对比“纯 prompt 修改”和“带 UI 上下文修改”的准确率、耗时和可审查性。
