输出步骤：

1. 先确认用户真实任务：不是做完整 AI 前端编辑器，而是让 AI 准确知道用户在页面上指的是哪里。
2. 定义第一性原理：用户看到的是运行页面，AI 修改的是源码，中间必须有可信上下文桥接。
3. 收敛 MVP：浏览器选中元素、提取上下文、传给 Agent、写回源码、预览、撤销、记录。
4. 明确不做：完整设计器、Git/PR、多项目管理、复杂权限、深度私有组件全覆盖。
5. 把产品需求拆成可验收 user stories、指标、风险和开放问题。

## 1. Executive Summary

我们要做一个本地可视化 AI 改码插件，服务于没有专职前端或前端资源不足的产品、设计、后端和全栈开发者。用户在本地 `localhost` 页面中发现文案、间距、颜色、布局等局部问题时，可以直接点选页面元素并用自然语言说明修改意图；系统将选中元素的 DOM、样式、源码线索、组件链和用户意图打包为结构化上下文，交给本地 AI Agent 修改源码，并提供预览、撤销和修改记录。目标是把“人看得见问题，但 AI 找不到位置”的断点补上，将样式返工次数从每个任务 3-5 次降低到 1-2 次以内。

一句话版本：

> 用户在浏览器里指哪里，AI 就知道改哪里，并且改错了能安全退回来。

## 2. Problem Statement

### 2.1 Who Has This Problem

主要用户：

- 产品/后端/全栈开发者：使用 AI 生成或维护前端页面，但不熟悉完整前端工程结构。
- 设计师：能识别页面视觉问题，希望直接指出问题位置，而不是先转译成代码描述。
- 前端开发者：也可使用该工具减少定位元素、查找组件和微调样式的时间，但不是第一优先用户。

使用场景集中在：

- AI 生成代码后的页面校正。
- 本地开发页面的 UI 走查。
- 复杂后台页面中的文案、间距、颜色、布局微调。
- 产品/设计反馈后，开发者需要快速定位对应源码并修正。

### 2.2 What Is The Problem

当前 AI 能写代码，但在本地页面样式修改场景中经常不知道“用户说的这里”对应哪个 DOM、组件、文件、样式来源和代码位置。

典型失败表现：

- 改错位置：AI 根据关键词找到相似组件或相似文案，但不是用户指的元素。
- 多改范围：为了满足一句模糊指令，AI 修改公共组件、全局样式或多个无关区域。
- 漏改：AI 修改了部分文案或样式，但没有覆盖真实问题所在状态。
- 返工：用户需要反复截图、描述、刷新、验证、再描述。

### 2.3 Why It Is Painful

用户影响：

- 每个前端任务通常返工 3-5 次，每次约 3-5 分钟，单任务约损耗 15-25 分钟。
- 团队每周约 4-8 小时耗在纯样式返工上，约占前端开发总时间 20-30%。
- 对非前端角色来说，问题不是“不知道想改什么”，而是“不知道怎么把页面对象翻译成代码上下文”。

业务影响：

- AI 生成前端的效率收益被后续样式返工抵消。
- 样式问题通常会在开发/测试阶段拦截，虽不一定流到线上，但持续消耗开发、走查和 review 时间。
- 内部私有组件、内网项目和复杂后台语义使外部通用工具难以直接覆盖。

### 2.4 Evidence

已确认：

- 问题高频：每次前端开发任务完成后查看页面样式时都会遇到。
- 成本可量化：每周约 4-8 小时样式返工，基于现有任务频率和返工次数估算。
- 核心假设有验证信号：定位准确时，AI 修改一次通过率可达 90%+。
- 提出者、使用者和受益者基本一致，不是“替别人痛”。
- 私有组件深封装会影响上下文获取，但占比不高，不阻塞第一阶段。

待确认：

- 真实业务项目中，元素到源码映射的稳定覆盖率。
- 每项目安装、全局注入、浏览器插件和 IDE/CLI 桥接的最佳工程接入方式。
- 结构化上下文传给不同 AI Agent 后的实际命中率差异。

## 3. First Principles

### 3.1 用户不是要一个“更大的编辑器”

用户真正要的是缩短路径：

> 看到页面问题 -> 指出具体对象 -> 表达修改意图 -> AI 改对代码 -> 看到结果 -> 不满意可恢复。

因此，第一版不应从完整可视化编辑器、设计器、低代码平台或 IDE 工作台出发，而应从“定位”和“可信修改”出发。

### 3.2 浏览器是问题发生地，源码是交付事实

用户在浏览器里发现问题，但最终交付物不是浏览器临时态，而是代码变更。

所以产品必须同时尊重两件事：

- 浏览器是用户表达问题的第一现场。
- 代码 diff / 文件变更才是真实交付结果。

### 3.3 AI 不是问题判断者，而是执行者

AI 不应凭空猜“这里”是什么。它需要结构化上下文：

- 被选中的元素。
- DOM 层级和文本。
- computed style 和关键 CSS 来源。
- 组件链和源码线索。
- 页面 URL、路由和视口信息。
- 用户补充的一句话修改意图。

### 3.4 低摩擦必须和可恢复绑定

本产品的体验性格应是快速、直接、低打扰。但只要系统默认写入源码，就必须同时具备：

- 写入前快照。
- 修改结果可见。
- 影响范围可查。
- 一键整组撤销。
- 失败自动恢复。

没有恢复能力，低摩擦会变成高风险。

## 4. Target Users & JTBD

### 4.1 Primary Persona：AI 前端协作者

角色：产品、后端、全栈、设计工程交叉角色。

背景：

- 需要交付或调整前端页面。
- 主要依赖 Cursor、Claude Code、Codex、Copilot、CLI Agent 等 AI 工具。
- 能看出页面问题，但不一定熟悉组件结构、样式来源和代码位置。

目标：

- 快速把本地页面调整到可接受状态。
- 不花大量时间解释“哪个按钮、哪个卡片、哪个区域”。
- 不因为 AI 误改而破坏本地项目。

痛点：

- 自然语言描述无法精准指向页面元素。
- 截图和标注只能说明视觉问题，不能稳定定位源码。
- IDE 搜索需要理解组件名、文件结构和 class 命名。
- AI 修改后需要反复检查是否改错、漏改、多改。

JTBD：

- Functional Job：在本地页面上指出目标元素，让 AI 快速修改正确代码。
- Emotional Job：对 AI 修改有控制感，不担心项目被改乱。
- Social Job：让设计/产品/后端之间的前端修改沟通更专业、更少返工。

### 4.2 Secondary Persona：前端开发者

目标：

- 减少查 DOM、找组件、定位样式来源的时间。
- 用 AI 做局部重复性样式修复。
- 保留代码审查和回滚能力。

差异：

- 前端开发者可以接受更多技术信息，例如 CSS、组件链、文件位置。
- 非前端用户更需要语义化表达，例如“供应商标题区域”“风险评分卡片”。

### 4.3 Affected Persona：测试 / Reviewer / 研发负责人

他们不是第一使用者，但会受影响：

- 如果工具可靠，样式问题会更早在开发阶段解决。
- 如果工具误改范围过大，会增加 review 和测试成本。
- 因此必须提供影响范围、记录、撤销和失败恢复。

## 5. Strategic Context

### 5.1 Why Now

AI coding 已经让非前端角色具备生成前端页面的能力，但“生成后校正”成为新的效率瓶颈。用户不是从零写页面，而是在真实页面和真实代码之间做大量小修小补。

行业趋势也在收敛到同一方向：

- Inspector 证明了 browser-first、selected element、runtime context、diff、Git/PR 的完整工作流价值。
- React Grab 证明了“选中 UI + 结构化上下文 + 外部 Agent”本身就是独立高价值切口。
- Cursor Browser / Design Sidebar 说明 AI IDE 正在吸收视觉编辑能力，但也暴露正确性、确定性和可信度风险。
- code-inspector、react-dev-inspector、LocatorJS 等项目说明 DOM 到源码定位已有成熟底层实践。

### 5.2 Internal Opportunity

内部工具的机会不在于复制通用竞品，而在于处理外部工具难以覆盖的上下文：

- 内网本地开发环境。
- 私有组件库和业务组件语义。
- 企业后台复杂状态、权限、路由和接口上下文。
- 内部设计系统 token 和组件规范。
- 组织内既有 AI Agent、IDE 和代码 review 流程。

### 5.3 Positioning

对使用 AI 写前端但经常在本地页面样式微调中返工的产品、设计、后端和全栈开发者，本插件是一个 browser-first 的 UI-to-Agent 上下文与安全改码工具。它不同于完整 IDE、低代码平台或可视化设计器，而是把用户在页面上点到的元素转成 AI 能可靠消费的代码上下文，并用预览、撤销和记录保证修改可信。

## 6. Solution Overview

### 6.1 Product Definition

本产品是一个运行在本地开发环境中的浏览器插件，配套一个本地连接层，用于把浏览器选中的 UI 元素转换成 AI Agent 可消费的结构化上下文，并在安全边界内触发源码修改。

第一版核心闭环：

1. 用户打开 `localhost` 页面。
2. 用户开启插件选择模式。
3. 用户 hover 和点击页面元素，确认目标对象。
4. 插件提取 DOM、文本、样式、选择器、组件链、源码线索和页面上下文。
5. 用户输入一句自然语言修改意图。
6. 系统生成结构化上下文包，交给本地 AI Agent。
7. Agent 修改本地源码。
8. 系统触发热更新或刷新。
9. 用户预览结果。
10. 用户可继续多轮微调，或撤销本次会话的全部变更。
11. 后台记录保留修改前后对比、影响文件、目标元素和状态。

### 6.2 Product Personality

- 快速：不让用户先学习复杂工作台。
- 直接：主流程围绕页面点选和一句话修改。
- 克制：第一版不做完整设计器和低代码搭建。
- 可信：任何写回源码的行为都要可回溯、可撤销、可解释。

### 6.3 MVP Scope

MVP 不是完整 Inspector，而是“比 React Grab 更贴近内部场景的安全上下文改码插件”。

MVP 必须成立的最小闭环：

> 选中元素 -> 提取上下文 -> 发送给 Agent -> 修改源码 -> 预览结果 -> 整组撤销。

## 7. Key Capabilities

### 7.1 页面元素选择

用户可在本地页面上开启选择模式，hover 时显示高亮，点击后锁定目标元素。

能力要求：

- 支持开启/关闭选择模式。
- hover 时展示边框、元素标签和基础尺寸。
- 点击后固定选中状态。
- 允许重新选择。
- 选择状态不能破坏页面原有交互。
- 仅在 `localhost`、`127.0.0.1` 或配置允许的本地开发域名生效。

### 7.2 上下文提取

系统需要把“用户点到的东西”转成 AI 能理解的结构化上下文。

上下文至少包括：

- 页面信息：URL、路由、viewport、浏览器环境。
- 元素信息：tag、文本、role、aria、data attributes、class、id。
- DOM 信息：父子层级、相邻上下文、可读摘要。
- 样式信息：关键 computed style、布局、间距、颜色、字体、尺寸。
- 源码线索：组件名、文件路径线索、行号线索、source map 线索。
- 视觉线索：元素截图或页面截图引用，MVP 可作为待确认增强项。
- 用户意图：用户输入的修改描述。

建议上下文包结构：

```json
{
  "target": {
    "elementLabel": "button",
    "text": "保存",
    "semanticName": "表单提交按钮",
    "selector": "...",
    "domPath": "...",
    "sourceHints": [
      {
        "component": "SaveButton",
        "file": "source hint only",
        "line": "source hint only",
        "confidence": "high"
      }
    ]
  },
  "styles": {
    "layout": {},
    "spacing": {},
    "typography": {},
    "color": {}
  },
  "page": {
    "url": "localhost page",
    "route": "current route",
    "viewport": {}
  },
  "userIntent": "把这个按钮改成主按钮样式，文案改成保存",
  "guardrails": {
    "preferLocalChange": true,
    "avoidGlobalStyleChangeWithoutConfirmation": true,
    "requireRollbackSnapshot": true
  }
}
```

### 7.3 自然语言修改

用户在选中元素后输入修改意图，系统将意图与上下文绑定。

支持类型：

- 文案修改。
- 间距修改。
- 颜色修改。
- 字号、字重、圆角等基础视觉属性。
- 局部布局调整。

约束：

- 修改应优先围绕选中元素和局部上下文。
- 如果需要修改公共组件、全局样式、设计 token 或多个文件，系统必须在记录中标记影响范围。
- 如果 Agent 判断目标不明确，必须要求用户重新选择或补充意图，而不是自行大范围猜测。

### 7.4 Agent 桥接与源码写回

第一版不重造 AI IDE，优先对接现有 Agent 能力。

能力要求：

- 生成结构化 prompt / context packet。
- 支持复制到外部 Agent，或通过本地连接层发送到指定 Agent。
- 写入源码前创建会话快照。
- 写入后触发热更新或刷新。
- 多轮指令归入同一修改会话。
- 失败时自动回滚到会话开始前状态。

### 7.5 预览、撤销和记录

只要支持自动写回源码，就必须支持恢复。

能力要求：

- 用户可一键撤销本次会话涉及的所有文件修改。
- 修改失败时自动撤销。
- 撤销后页面回到修改前状态。
- 后台记录包含：
  - 选中元素。
  - 用户指令。
  - 上下文摘要。
  - 修改文件。
  - 修改前后 diff。
  - 成功、失败、撤销状态。
  - 失败原因摘要。
  - 影响范围。

### 7.6 风险分级

为平衡低摩擦和可信度，修改分为三类：

| 修改类型 | 示例 | 默认策略 |
|---|---|---|
| 低风险局部修改 | 文案、单元素颜色、单元素间距 | 可直接应用，但必须可撤销 |
| 中风险局部结构修改 | 调整局部布局、修改组件 props | 应展示影响范围摘要 |
| 高风险扩散修改 | 全局样式、公共组件、token、多个页面 | 必须二次确认或进入审查态 |

## 8. User Flow

### 8.1 Happy Path

1. 用户打开本地页面。
2. 用户发现某个按钮文案不准确。
3. 用户打开插件面板，开启选择模式。
4. 页面 hover 出现高亮。
5. 用户点击按钮。
6. 插件显示“已选中：按钮 / 表单提交区域 / 源码线索可信度高”。
7. 用户输入：“把这个按钮文案改成保存，并使用主按钮样式。”
8. 系统生成上下文包并发送给 Agent。
9. Agent 修改本地源码。
10. 页面热更新。
11. 用户看到结果。
12. 用户点击“保留”，或继续输入“再窄一点”。
13. 会话记录写入后台。

### 8.2 Undo Path

1. 用户发现修改不符合预期。
2. 用户点击“撤销本次会话”。
3. 系统还原本次会话开始前的文件快照。
4. 页面刷新。
5. 记录状态变为“已撤销”。

### 8.3 Failure Path

1. Agent 修改多个文件时出现构建失败或写入异常。
2. 系统检测失败。
3. 系统自动撤销已产生变更。
4. 页面回到修改前状态。
5. 用户看到失败摘要，例如“未能稳定定位组件，已撤销修改”。

## 9. Success Metrics

### 9.1 Primary Metric

AI 修改命中率：

- 定义：用户选中元素并发起修改后，第一次或第二次修改即命中目标元素且未产生明显无关修改的比例。
- 当前基线：纯自然语言场景常需 3-5 次返工。
- 目标：MVP 试点中，80% 以上任务在 1-2 次内完成。
- 理想目标：定位准确场景一次通过率接近或超过 90%。

### 9.2 Secondary Metrics

- 单个样式问题从发现到看到可接受结果的耗时：从 15-25 分钟降到 5-8 分钟以内。
- 每周样式返工时间：从 4-8 小时降低 50% 以上。
- 撤销成功率：100%。
- 修改记录完整率：100% 记录目标元素、用户意图、影响文件和状态。
- 源码定位覆盖率：在试点项目中，80% 以上业务页面元素能给出可用源码线索。

### 9.3 Guardrail Metrics

- 无关文件修改率：低于 10%，且必须可被记录识别。
- 回滚失败次数：0。
- 本地项目因工具修改进入不可恢复状态：0。
- 用户需要手动修复工具失败残留的次数：0。

## 10. User Stories & Acceptance Criteria

### Story 1：开启选择模式

As a 用户, I want 在本地页面上开启选择模式, so that 我可以直接指出要修改的元素。

Acceptance Criteria:

- 用户可从插件面板开启和关闭选择模式。
- 开启后，hover 元素时出现明显高亮。
- 高亮不应改变页面布局。
- 点击元素后，系统固定选中状态。
- 用户可重新选择元素。
- 选择模式只在允许的本地开发域名生效。

### Story 2：确认目标元素

As a 用户, I want 看到当前选中了什么, so that 我能确认 AI 不会改错对象。

Acceptance Criteria:

- 选中后显示元素标签、文本摘要、基础尺寸。
- 如果可识别组件名或源码线索，展示摘要。
- 如果无法识别源码线索，明确提示“源码定位置信度低”。
- 用户可取消选择或重新选择。

### Story 3：提取结构化上下文

As a 用户, I want 插件自动提取页面和源码上下文, so that 我不用手动描述 DOM、class、组件和文件位置。

Acceptance Criteria:

- 系统能提取 DOM、文本、class、id、role、aria 和关键 data attributes。
- 系统能提取关键 computed style。
- 系统能生成 DOM 层级摘要。
- 系统能输出源码线索及置信度。
- 上下文包能被复制或发送给 Agent。

### Story 4：输入自然语言修改意图

As a 用户, I want 对选中元素输入一句修改指令, so that AI 能把“指哪里”和“怎么改”绑定起来。

Acceptance Criteria:

- 用户必须先选中元素或明确使用当前目标。
- 输入框支持自然语言描述。
- 用户指令和目标元素写入同一上下文包。
- 用户可连续输入多轮指令。
- 多轮指令默认归入同一修改会话。

### Story 5：Agent 修改源码

As a 用户, I want AI 根据选中元素上下文修改本地源码, so that 我能快速看到真实代码变更后的页面结果。

Acceptance Criteria:

- 系统在写入前创建会话快照。
- 系统将上下文包和用户意图发送给 Agent。
- Agent 可修改一个或多个相关文件。
- 修改范围必须记录。
- 写入后触发热更新或页面刷新。
- 如果 Agent 无法确定修改位置，应返回澄清或失败，不应盲目扩散修改。

### Story 6：预览结果

As a 用户, I want 看到修改后的本地页面, so that 我能判断是否接受本次修改。

Acceptance Criteria:

- 修改后页面自动刷新或等待项目热更新。
- 插件显示本次修改状态。
- 用户可以继续输入下一轮指令。
- 用户可以撤销整个会话。

### Story 7：整组撤销

As a 用户, I want 一键撤销本次会话所有修改, so that 我可以放心让 AI 直接尝试。

Acceptance Criteria:

- 撤销粒度为整个会话，不是最后一步。
- 撤销恢复所有本次会话涉及文件。
- 撤销后页面恢复到会话开始前状态。
- 撤销状态写入记录。
- 撤销失败必须提示原因，并保留可手动恢复线索。

### Story 8：失败自动恢复

As a 用户, I want 修改失败时系统自动恢复, so that 本地项目不会停留在半成品变更里。

Acceptance Criteria:

- 写入异常、构建失败、Agent 中断或文件冲突时，系统进入失败恢复。
- 已写入文件自动回滚。
- 用户看到可理解失败摘要。
- 失败记录可在后台查看。

### Story 9：修改记录

As a 用户, I want 查看修改记录和影响范围, so that 我能理解 AI 改了哪里，也方便 review。

Acceptance Criteria:

- 每次会话生成一条记录。
- 记录包含目标元素、用户意图、上下文摘要、修改文件、diff、状态。
- 记录支持查看成功、失败、撤销结果。
- 记录默认后台查看，不打断主流程。

### Story 10：风险分级提示

As a 用户, I want 在高风险修改前得到提示, so that 我不会无意识修改公共组件或全局样式。

Acceptance Criteria:

- 当修改涉及公共组件、全局样式、token 或多个页面时，系统标记为高风险。
- 高风险修改必须提示影响范围。
- 高风险修改不得静默写入。
- 用户可选择继续、取消或改为生成建议。

## 11. AI System Requirements

### 11.1 Agent 输入要求

AI Agent 接收的输入必须结构化，不应只给自然语言。

输入应包括：

- 用户目标元素。
- 页面上下文。
- 样式上下文。
- 源码定位线索。
- 修改意图。
- 修改约束。
- 风险边界。

### 11.2 Agent 行为约束

Agent 必须遵守：

- 优先修改局部相关代码。
- 不确定时返回澄清，不做大范围猜测。
- 修改公共组件前说明影响范围。
- 不引入无关重构。
- 不擅自改动与用户意图无关的页面。
- 输出修改摘要和风险说明。

### 11.3 Evaluation Strategy

需要建立最小评测集，覆盖：

- 文案修改。
- 按钮样式修改。
- 卡片间距修改。
- 标题颜色修改。
- 局部布局修改。
- 公共组件误改风险。
- 源码定位失败。
- 深封装组件无法定位。
- 多轮微调。
- 撤销和失败恢复。

每个测试用例记录：

- 是否命中目标元素。
- 是否改对文件。
- 是否产生无关修改。
- 是否一次通过。
- 是否可撤销。
- 用户是否需要手动补救。

## 12. Technical Specifications

### 12.1 Architecture Overview

建议模块：

- Browser Extension：负责插件面板、选择模式、hover/selected overlay、用户指令输入。
- Page Injector：负责 DOM 扫描、事件拦截、样式读取和上下文提取。
- Source Mapping Layer：负责从 DOM/组件/source map/框架调试信息推导源码线索。
- Local Bridge：负责和本地项目、Agent、文件系统交互。
- Agent Adapter：负责连接 Codex、Claude Code、Cursor、Copilot CLI 等外部 Agent。
- Change Session Manager：负责快照、diff、撤销、失败恢复和记录。
- History Viewer：负责后台记录查看。

### 12.2 Integration Points

- 浏览器：Chrome / Chromium 优先。
- 本地页面：`localhost`、`127.0.0.1`、用户配置的本地域名。
- 前端框架：React 优先；Vue、纯 HTML/CSS 作为后续验证。
- 源码定位：优先复用 source map、React 组件调试信息、LocatorJS / code-inspector / react-dev-inspector 类能力。
- Agent：第一阶段优先支持复制 context packet；随后支持本地 Agent adapter。

### 12.3 Security & Privacy

- 默认仅允许本地开发域名。
- 不上传源码到云端，除非用户明确配置云端 Agent。
- 修改记录默认本地保存。
- 用户可清空记录。
- 不支持线上页面写回。
- 不读取与当前项目无关的文件。

### 12.4 Performance

- 选择模式不得明显影响页面交互性能。
- hover 高亮延迟应低于 100ms。
- 上下文提取应在 1s 内完成基础信息采集。
- 源码线索提取如超过 2s，应先返回基础上下文并提示“源码线索仍在分析”。

## 13. Out of Scope

本期不做：

- 完整可视化设计器。
- 完整属性面板。
- 拖拽搭建页面。
- 设计稿同步。
- Figma 双向同步。
- 多项目管理。
- 团队权限体系。
- Git commit / PR / MR 闭环。
- 云端历史保存。
- 线上页面写回。
- 生产环境发布。
- 全量框架适配。
- 私有组件深封装 100% 定位。
- 全栈日志、数据库、接口上下文。
- 自动生成完整页面。
- 替代 Cursor、Claude Code、Codex 或 IDE。

未来可考虑：

- Design 面板：间距、颜色、排版、尺寸等高频属性。
- 设计系统 token 映射。
- 业务语义识别。
- Git / MR / PR 流程。
- 团队审计和权限。
- 运行时日志和接口上下文。

## 14. Dependencies & Risks

| 风险 | 影响 | 应对 |
|---|---|---|
| 源码定位不稳定 | Agent 仍会猜文件，价值下降 | 先选 1-2 个真实项目试点，记录定位覆盖率 |
| 私有组件深封装无法识别 | 部分场景不可用 | 明确边界，先覆盖业务页面元素和浅层组件 |
| 默认直接应用导致误改 | 用户不敢用 | 快照、撤销、失败恢复、风险分级必须先做 |
| 修改公共组件影响多个页面 | 增加 review 和测试成本 | 公共组件/全局样式修改进入高风险提示 |
| 插件影响页面交互 | 干扰开发调试 | 选择模式可开关，事件拦截最小化 |
| Agent 输出不可控 | 产生无关重构 | prompt guardrails、diff 记录、无关修改检测 |
| 外部 Agent 接入差异大 | 体验不一致 | 第一阶段先支持复制 context packet，再做 adapter |
| 用户误以为工具替代 review | 责任边界不清 | 明确代码质量仍由开发者负责，工具负责上下文和恢复 |

## 15. Phased Roadmap

### Phase 0：真实项目验证

目标：验证元素选择和源码定位是否足够稳定。

范围：

- 1-2 个真实本地页面。
- 元素 hover / select。
- DOM / 样式 / 源码线索提取。
- context packet 复制。
- 手动粘贴到现有 Agent。

退出标准：

- 80% 以上业务页面元素能生成可用上下文。
- 通过上下文修改的命中率明显高于纯 prompt。

### Phase 1：安全改码闭环

目标：形成最小产品闭环。

范围：

- 插件面板。
- 选择模式。
- 自然语言指令。
- 本地 Agent adapter。
- 快照。
- 源码写回。
- 预览。
- 整组撤销。
- 修改记录。

退出标准：

- 80% 以上样式修改任务 1-2 次完成。
- 撤销成功率 100%。
- 无不可恢复文件损坏。

### Phase 2：可信编辑增强

目标：提升复杂场景可用性和团队信任。

范围：

- diff review。
- 风险分级增强。
- 低风险属性面板。
- token 建议。
- 组件 props / variant 识别。
- Open in Editor。

### Phase 3：复杂业务上下文

目标：面向企业后台和内部平台增强。

范围：

- 业务语义识别。
- 设计系统 token 深度接入。
- 路由、权限、接口、日志上下文。
- Git / MR / PR。
- 团队审计。

## 17. PRD Self-Assessment

最强部分：

- 问题定义和需求成立性。已有明确场景、频率、成本、角色边界和竞品证据。

最弱部分：

- 技术接入路径和真实项目源码定位覆盖率。当前仍缺内部项目实测数据，不能假设所有 DOM 都能稳定映射到源码。

最高风险假设：

| 假设 | 风险 | 验证 |
|---|---|---|
| 业务页面元素大多能提取可用源码线索 | 如果错，产品会退化为截图/标注工具 | 真实页面 50 个元素样本测试 |
| 结构化上下文能显著提升 Agent 命中率 | 如果错，ROI 不成立 | 同一任务对比纯 prompt 和 context packet |
| 用户愿意接受默认直接应用源码 | 如果错，需要前置 diff/Apply | 可用性测试比较直接应用和先审查 |
| 整组撤销可以稳定恢复 | 如果错，不能上线自动写回 | 文件快照和失败恢复压测 |

建议下一步：

先做 Phase 0 验证原型，不做完整工作台。用真实内部页面验证 3 件事：

1. 点选元素后，能否稳定提取 DOM、样式和源码线索。
2. 加入 context packet 后，Agent 修改命中率是否显著高于纯自然语言。
3. 写回加撤销的安全闭环是否足够可靠。

只有这三件事成立，才进入 Phase 1 的自动改码插件。
